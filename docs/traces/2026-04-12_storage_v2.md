# Storage V2 Trace

Date: `2026-04-12`

## Scope

This trace records the first measured comparison between:
- storage format `v1`: text vector payloads
- storage format `v2`: binary little-endian vector payloads with text manifests and metadata

The goal was not to guess whether binary storage would help, but to measure:
- artifact byte size
- warm-load latency
- compatibility with legacy `v1` caches

## Validation

Correctness and compatibility commands:

```bash
pixi run test_storage
pixi run test_storage_compat
pixi run test_storage_invariants
```

All passed.

Compatibility boundary validated:
- new `v2` payloads roundtrip correctly
- corrupted binary payloads are rejected
- legacy `v1` text payloads still load

## Benchmark Command

```bash
pixi run bench_profile_storage_real_subset_raw
```

This was a same-process raw comparison between synthesized `v1` and `v2` artifacts for the same stored real-subset tasks and indexes.
For this specific benchmark, the signal is strong enough that the relative difference is meaningful even without a quiet-wrapper run:
- both formats are compared in the same process
- the deltas are tens of times, not single-digit percentages

## Interpretation

What the evidence supports:
- `v2` reduces artifact size by roughly `2.7x-2.8x`
- `v2` improves warm judged-task load by roughly `37x`
- `v2` improves warm packed-index load by roughly `45x`
- binary vector payloads are worth keeping as the new default storage format

What the evidence does not claim:
- absolute cold-start disk performance across machines
- any direct search-quality change, because storage format should not affect retrieval semantics

Current conclusion:
- keep `v2` as the default save format
- retain `v1` read compatibility until there is a strong reason to remove it
